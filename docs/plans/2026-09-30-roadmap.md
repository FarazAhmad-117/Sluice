# Sluice build roadmap

Derived from `docs/plans/2026-09-30-sluice-architecture-design.md`. Each phase
gets its own task-by-task plan when it starts, written against what the earlier
phases actually produced. Only Phase 1 has one today.

## Phase order

```
1 Freeze the protocol ──► 2 Restructure ──► 3 Kill-switch fixes ──► 4 Spec + Rust check ──► 5 Rust CLI
                                                     │
                                                     └──► 6 Dashboard: recovery, teams, audit ──► 7 Mobile + PWA
                                                                                                        │
                                                                    5 + 7 ──► 8 Launch readiness ◄──────┘
                                                                                       │
                                                                                       └──► 9 Self-host (when triggered)
```

Phases 6 and 7 run alongside 4 and 5 once Phase 3 is merged.

## 1. Freeze the protocol

**Plan:** `docs/plans/2026-09-30-phase-1-freeze-the-protocol.md`

Everything that becomes permanent the moment a real account stores a secret:
stable client-generated IDs, `v2` encryption bindings on those IDs, a random
per-account salt with two-phase login, the dashboard's invented constants moved
into `@sluice/crypto`, and `orgId` on every org-owned row.

**Exit:** every test green; a fresh signup, org, environment, secret, token and
`sluice run` work end to end; no Convex document ID reaches any encryption
binding.

**Status:** implemented 2026-10-01 on branch `phase-1-freeze-protocol`. The plan's
"Outcome" section records what shipped and what it left open. The follow-ups
are listed below under the phase that owns each one.

## 2. Restructure the repository

Move `convex/` to `packages/backend/`, `apps/admin` to `apps/dashboard`,
`packages/sdk` to `packages/sdk-node`; move backend dependencies out of the root
`package.json`; add the CI checks for the dependency rules in design section 14.

**Exit:** the same test count as before the move, all green; CI enforces rules 1,
2 and 4.

**From Phase 1:** the `apps/admin` vitest config repeats the aliases in
`vite.config.ts`. Make one the source of the other during the move, so the two
cannot drift.

## 3. Kill-switch fixes

- **A.** `getBundle` answers an authentic expired pass with notices only.
- **C.** Org root key, revocation-key certificates, certificate floor; the
  single-string token that carries the cell hostname and pinned root.
- **B, server half.** The per-environment offline allowance setting. The cache
  itself is CLI work, in Phase 5.

**Exit:** a test proves a revocation reaches a process whose pass expired while
offline; the TypeScript CLI pins the root and accepts the one-string token.

**From Phase 1:** the single-string token also carries the environment's
permanent uid, minted on the client. The CLI then pins the name-to-uid mapping
itself. Today the uid it binds every secret and grant to is the one the server
puts in the bundle, so a malicious server can name the wrong environment. This
pins it for the CLI only; the dashboard's mapping is a Phase 6 item.

**From Phase 1, near-term:** each device remembers the salt for every account
that has logged in on it and refuses a different one. Moving the salt
server-side let a compromised server hand every account the same salt and
amortise one dictionary across every verifier it receives; under v1 the
client computed the salt from the address, so the server could not choose it.
With the salt remembered, a server can attempt this only on a device's first
login. Not tied to the kill-switch work; it lands with this phase or sooner.

## 4. Spec, vectors and the Rust client check

Verify the Convex Rust client supports subscriptions and the auth the handshake
needs. Write `spec/protocol.md`. Generate `spec/vectors/` from
`@sluice/crypto`.

**Exit:** a Rust spike subscribes to `getBundle` on the dev deployment and
receives a pushed update; the vectors file covers every construction in
`protocol.ts`, `muk.ts`, `identity.ts` and `token.ts`.

**If the spike fails,** stop and revisit the CLI language before Phase 5.

## 5. The Rust CLI

`sluice run` first, at parity with the TypeScript shell's four obligations, then
signal forwarding and child reaping, the startup cache, and `login`, `import`,
`token create`, `revoke`, `recover`. Release with `dist`: brew, scoop, winget,
shell and PowerShell installers, the npm wrapper, a Docker image, the
`setup-sluice` GitHub Action.

**Exit:** the Rust crypto passes every vector; the kill-switch tests from Phase 3
pass against the Rust binary; `packages/cli` is deleted.

**HARD REQUIREMENT, from Phase 1:** `sluice revoke`, and any other client that
signs a revocation (including a dashboard token screen, whenever it is built),
calls `revocationKeyMatches` on the unwrapped seed against the org's stored
revocation public key before signing, and refuses to sign on a mismatch.
`orgs.revocationPublicKey` is a column no ciphertext binds, so without this
check a server can substitute its own key while every grant still opens. The
check exists in `apps/admin/src/lib/orgs/revocation-key.ts` and nothing calls
it yet. Phase 3's root key and revocation-key certificates change what a
workload pins, so the check must be restated against the certified key when
that lands.

## 6. Dashboard: recovery, teams, audit

Recovery kit and emergency kit at signup; org recovery kit; invites with the
fragment secret; confirmation; roles; removal with key rotation and the
rotate-at-source checklist; the new audit events, hash chain, retention and
export.

**Exit:** a second admin can restore a user who lost password and kit; a
substituted public key fails the invite vouch.

**From Phase 1:**

- A client-side version ratchet: each client remembers the highest secret
  version and key version it has seen and refuses a lower one. The `v2`
  bindings stop splicing, not wholesale rollback of a row with its own old
  version. Forks and omissions need the ratchet compared across clients, or a
  transparency log.
- Audit events carry `secretUid` and the version once the audit metadata
  validator exists.
- Key rotation bumps every re-sealed secret's version. Re-sealing at the same
  version puts two rows under one (secret, version) and breaks the uniqueness
  the `by_secret_version` lookup relies on.
- The dashboard pins the environment name to uid mapping instead of taking
  the server's answer each time. Without it, a server that answers
  "production" with another environment's uid makes the dashboard show that
  environment's secrets as production's and seal every secret written to
  "production" into it. The Phase 3 token fixes this for the CLI only.
- A client-held secret key in the 1Password style, so the password is never
  the only input to the master key. The near-term salt memory is in Phase 3.
- Any dashboard screen that signs a revocation meets the Phase 5 hard
  requirement: `revocationKeyMatches` before signing.

## 7. Mobile and PWA

Responsive pass over every dashboard screen; installable PWA; service worker
caching the shell only; session storage that survives a restart; auto-lock;
passkeys with PRF unlock; TOTP; org-required MFA; push notifications.

**Exit:** revoke a token from a phone, from a cold start, in under ten seconds.

**From Phase 1:** a render test for the dashboard's `AuthProvider`, once a DOM
test library is added. Its flows are tested today, its rendering is not.

## 8. Launch readiness

Per-org beta limits, rate limits, terms of service, privacy policy, a live status
page, `SECURITY.md` updated for every change above, and one real GitHub Actions
run against a real deployment.

## 9. Self-host (when triggered)

One self-hosted Convex behind Caddy with backups, when the free plan runs out.
Cells follow the phases in design section 13.
